# BIPS v3 — План: Активация покупателя + UX доработки

**Цель:** покупатель получает устройство, подключает к WiFi, привязывает к своему аккаунту XiaoZhi — без помощи продавца.

---

## Проблема

Сейчас наш OTA URL (`158.160.216.45/bips-ota/ota.json`) отдаёт статический JSON без секции `activation`. Покупатель не может привязать устройство к своему аккаунту — код активации не появляется.

Стоковый сервер (`api.tenclass.net/xiaozhi/ota/`) умеет:
- Возвращать `activation: {code, challenge, message}` для незарегистрированных устройств
- Отдавать `websocket`/`mqtt` настройки
- Обрабатывать HMAC challenge при привязке

Но мы не можем просто вернуться на стоковый URL — тогда мы теряем контроль над версиями прошивки.

---

## Решение: OTA Proxy

Сервер (`158.160.216.45`) проксирует запрос OTA на стоковый API, но подменяет только секцию `firmware`.

### Схема работы

```
Устройство → POST 158.160.216.45/bips-ota/ota.php
    ↓
OTA Proxy:
    1. Пересылает запрос на api.tenclass.net/xiaozhi/ota/ (с теми же заголовками)
    2. Получает ответ от стокового API
    3. Парсит JSON
    4. Заменяет секцию firmware на НАШУ (версия + URL нашего бинарника)
    5. Возвращает объединённый JSON устройству
```

### Что отдаёт прокси

```json
{
    "server_time": { ... },           ← от стокового API
    "firmware": {                      ← НАША подмена
        "version": "4.1.7",
        "url": "http://158.160.216.45/bips-ota/xiaozhi.bin"
    },
    "activation": { ... },             ← от стокового API (если есть)
    "websocket": { ... },              ← от стокового API
    "mqtt": { ... }                    ← от стокового API (если есть)
}
```

### Реализация

**Файл:** `/home/openclaw/bips-ota/ota.php` (PHP, уже есть nginx + php-fpm на сервере)

Логика:
1. Читает тело запроса от устройства
2. Формирует POST на `https://api.tenclass.net/xiaozhi/ota/` с теми же заголовками (`Device-Id`, `Client-Id`, `Serial-Number`, `Activation-Version`, `User-Agent`, `Accept-Language`)
3. Получает JSON ответ
4. Парсит ответ, заменяет `firmware` на свою версию из конфига
5. Отдаёт результат

**Конфиг прокси** (файл рядом с ota.php):
```json
{
    "firmware_version": "4.1.7",
    "firmware_url": "http://158.160.216.45/bips-ota/xiaozhi.bin"
}
```

### Nginx конфиг

```nginx
location /bips-ota/ota {
    fastcgi_pass unix:/var/run/php/php-fpm.sock;
    fastcgi_param SCRIPT_FILENAME /home/openclaw/bips-ota/ota.php;
    include fastcgi_params;
}
location /bips-ota/ {
    alias /home/openclaw/bips-ota/;
    autoindex off;
}
```

## Задачи

### Фаза 1: OTA Proxy (активно)

- [ ] Написать `ota.php` — проксирует на стоковый API, подменяет firmware
- [ ] Настроить nginx — `/bips-ota/ota` → PHP, `/bips-ota/` → статические файлы
- [ ] Протестировать: запрос от устройства → получить activation code
- [ ] Протестировать: запрос от зарегистрированного устройства → получить firmware update
- [ ] Обновить `ota.json` — убрать (больше не нужен как статический файл)
- [ ] Обновить `scripts/pre_ota_check.py` — проверять ota.php и конфиг
- [ ] Задеплоить на сервер

### Фаза 2: UX доработки (после proxy)

- [ ] Скрывать время до NTP синхронизации — не показывать часы пока RTC не обновлён
- [ ] Индикатор заряда батареи — показывать на экране чтобы покупатель знал когда заряжать
- [ ] Приветственное сообщение при первом включении — "Привет! Я Бибс. Подключись к моей WiFi точке чтобы настроить меня."

### Фаза 3: Тестирование пути покупателя

- [ ] Сброс устройства до заводского состояния (стереть NVS)
- [ ] Пройти полный путь: включение → WiFi config → подключение → активация → привязка
- [ ] Задокументировать пошаговую инструкцию для покупателя

## Путь покупателя (после реализации)

1. Покупатель получает устройство
2. Включает → видит "Подключись к WiFi BIPS-XXXXXX"
3. Подключается телефоном к точке доступа
4. Открывает `192.168.4.1`, вводит WiFi пароль
5. Устройство подключается к WiFi
6. Делает запрос на наш прокси → прокси запрашивает стоковый API
7. Стоковый API видит незарегистрированное устройство → возвращает activation code
8. Устройство показывает код на экране + произносит голосом
9. Покупатель идёт на `xiaozhi.hello.com`, вводит код
10. Устройство привязано → работает

---

## Риски

- Стоковый API может блокировать запросы с нашего IP → нужен User-Agent как у реального устройства
- Стоковый API может изменить формат ответа → мониторинг
- Если стоковый API недоступен → устройство не может активироваться → fallback на наш статический ota.json
